# MySQL migration plan

Move the Phase 15 persistence foundation immediately after isolated Linux staging and before Phase 02. Retain Phase 15 for application-wide parity, migration rehearsal and cutover acceptance. Both steps require separate approval. SQLite continues to support selected fast tests. The current runtime rejects MySQL and uses SQLite for accounts, sessions, stations, pairing, automation, schedules, audit and Program state.

1. Inventory every direct SQLite call and seed path. Map entities, ownership, foreign keys, deletes, unique keys, indexes, timestamp precision, JSON and BLOBs. Compare the actual schema with Prisma. Define email case and collation explicitly. Record which queries use SQLite upserts, `INSERT OR IGNORE`, SQLite functions, triggers and write locks. Query prepared statements with bound parameters in both adapters.
2. Introduce async persistence contracts for sessions, audited transactions, station ownership and Program runtime state before expanding accounts or channels. Use InnoDB transactions and constraints to make pairing consumption, refresh rotation, scheduling leases, audit writes and operation idempotency atomic. Use per-channel locks and fencing, bounded retry for deadlocks and explicit connection budgets. Test concurrent writes and fail-closed organization checks against real MySQL.
3. Define immutable media references by organization, channel, object ID, digest, length and format. Classify PCM and frames as regenerable derived data where source/normalization versions exist. Preserve bytes needed to reproduce active assets until independently decoded. Move preview/media, PCM and frame objects to private file/object storage with a verified manifest. Do not put full-length movies in MySQL BLOBs.
4. Build separate runtime, migrator, backup and read-only diagnostic identities. Runtime gets only needed SQL and schema access. Stage forward-only versioned DDL, use TLS across hosts, keep credentials outside images and prevent accidental production restores.
5. Rehearse from a sanitized SQLite backup to a fresh MySQL database and isolated media destination. Verify row counts per organization, uniqueness, foreign keys, time zones, media digests, schedules, channel/provider identity, role boundaries, telemetry and competing workers. Decide explicitly whether sessions are migrated or revoked during cutover. Restore both SQL and media on a new target, then repeat cross-tenant, playback and failover checks.
6. Production cutover requires approval and a maintenance window. Snapshot SQLite, media references and application release, protect key backups, fence writes and execute the measured final delta. Keep independent output on the approved continuity path and reconcile runtime state before granting new control writes. Abort on parity, authorization, restore or receiver-budget failure.

Rollback before new MySQL writes by restoring the previous control binaries and pointing them to the intact SQLite and media snapshot. After new writes begin, replay a rehearsed compatible change journal or restore with the owner-approved data-loss budget and reconciliation plan. Never flip back silently or overwrite the active database. Retain protected evidence for both directions.
